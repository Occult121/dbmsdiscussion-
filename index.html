Acid properties of a transaction :
a transaction is a unit of program execution that accesses and or possibly updates various data items . acid properties of a transaction are :
Atomicity : either transaction executes in entirety or none executes at all
Consistency : state of database remains same both before and after transaction, despite system changes
Isolation : despite system changes , transaction executes independently of others
Durability : any modifications made to database as a result of transaction,persist even if there are system changes
e.gs there ‘s a schedule involving 2 accounts a and b, initial values in a and b accounts are $ 1000 and $ 2000 .
A transaction occurs that transfers $ 50 from a -b , as a result , final values in a and b becomes $ 950 and $ 2050 , clearly a consistent state ,
as sum a +b is preserved both before and after the transaction .
we now suppose that a hd crash occur after write – a committed but before write – b committed . so, now the final values in a and b accounts become $ 950
and $ 2000 , clearly a inconsistent state , as sum a +b is no longer preserved both before and after the transaction .
even if system failure did not occurred and transaction proceeded to completion,
this inconsistent state would not have been visible except during occurrence of transaction.
This again reflects Atomicity . isolation preserved . durability preserved through recovery mgmt.. component of transactions

phantom deadlock : we have 2 transactions a and b that execute individually as foll.
INSERT INTO ACCOUNT VALUES (“RS”, “SAVINGS”, 2000);
SELECT FROM ACCOUNT VALUES(“RS”, “SAVINGS”, 2000);
If these 2 transactions occur separately , they execute but if made to run concurrently ,
effectively the schedule does not execute at all and deadlock , called as “phantom deadlock” creeps in place
Phantom deadlock can be resolved if assumed that a – lock data items in exclusive mode & b – lock data items in shared mode
